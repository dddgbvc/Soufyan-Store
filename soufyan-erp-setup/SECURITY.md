# SECURITY — Soufyan ERP Setup V7

نموذج الأمان والتهديد لمعالج الإعداد وبوابة الدخول، ولما يسندهما على
Supabase. مكتوب ليُقرأ قبل التشغيل الحقيقي لا بعده.

المرافق: [`AUDIT-V7.md`](AUDIT-V7.md) — ما كان مكسورًا في V6، وكيف أُثبت، وكيف أُصلح.

---

## 1. القاعدة الحاكمة

> لا شيء يأتي من المتصفح يُعدّ حدًّا أمنيًا.

`localStorage` و`sessionStorage` و hash العنوان والحقول المخفيّة وحالة الواجهة
ومصفوفة الصلاحيات والدور و`terminalId` و`setup_completed` — كلها **مدخلات غير
موثوقة**. المتصفح يعرض ويُدخِل ويحتفظ بحالة عرض؛ والخادم يقرّر.

عمليًا في هذا المشروع:

| القرار | مَن يقرّره |
|---|---|
| من أنت | Supabase Auth |
| ما دورك | `profiles.role` / `employees.role` على الخادم |
| ما صلاحياتك | `permissions_for(role)` على الخادم |
| هل جلستك حيّة | `app_session_whoami()` |
| هل هذا جهازك | `app_sessions.terminal_id` (مقارنة على الخادم) |
| هل اكتمل الإعداد | `setup_state.completed` عبر `setup_status()` |
| هل يُسمح بهذه المهمة | دالة الحافة `setup-provision` |

ما يحتفظ به المتصفح: مؤشّر جلسة، ومعرّف جهاز، وتقدّم المعالج، وآخر هوية معروفة
للعرض. لا شيء من ذلك يمنح صلاحية.

## 2. نموذج التهديد

### المهاجمون المفترضون

| # | مَن | ماذا يملك | ما يريده |
|---|---|---|---|
| A1 | زائر على الإنترنت | المفتاح العلني (anon) — وهو في كل نسخة من الواجهة | الوصول إلى بيانات المحل أو إنشاء حساب امتياز |
| A2 | موظف بصلاحية محدودة | حساب حقيقي بدور `CASHIER` | ترقية نفسه إلى `ADMIN` |
| A3 | من يمسك بالجهاز دقيقة | متصفّح مفتوح وأدوات المطوّر | جلسة إدارية |
| A4 | من نسخ `localStorage` | ملف حالة من جهاز آخر | استئناف جلسة ليست له |
| A5 | شبكة معادية | اعتراض وتكرار الطلبات | إعادة استعمال رمز أو جلسة |
| A6 | مُدخِل بيانات | حقول الإعداد | XSS مخزَّن يصيب من يفتح المراجعة |

### ما هو خارج النطاق

* أمان التطبيق الحيّ نفسه (نقطة البيع، وحدة الشراء، بوت تيليغرام) — لا يوجد
  مصدره في هذا المستودع. ما يخصّه مذكور في §9.
* اختراق حساب Supabase الإداري أو تسريب `service_role`. إن حدث فكل شيء ساقط.
* الوصول الفيزيائي المستمر إلى جهاز مفتوح بجلسة صالحة.

## 3. نموذج التوثيق

### المستخدم الجديد

```
البريد ──▶ POST /auth/v1/otp        (Supabase يرسل رمزًا من ٦ خانات)
       ──▶ POST /auth/v1/verify     (نجاحه = إنشاء الحساب وتأكيد بريده)
       ──▶ PUT  /auth/v1/user       (كلمة المرور على الحساب نفسه)
       ──▶ setup-provision × 7      (تهيئة على الخادم، بجلسة هذا المستخدم)
       ──▶ finalize                 (المالك يصير ADMIN بمفتاح الخدمة)
```

**«توثيق البريد» و«إنشاء الحساب» حدث واحد.** لا توجد حالة وسطى يكون فيها البريد
«موثَّقًا» بلا حساب — وهي الحالة التي كانت V6 تكتبها في الواجهة بلا أثر على أي
خادم.

### المستخدم العائد

```
POST /auth/v1/token?grant_type=password
  ──▶ rpc app_session_start_authenticated(terminal_id, …)
        الخادم: يتحقّق من profiles، يربط صف الموظف، يفتح جلسة موسومة بالهوية،
                ويعيد { session_id, employee{role}, permissions }
```

`p_employee_id` ليس وسيطًا يرسله العميل: الهوية تُشتقّ من `auth.uid()`.

### الاستئناف بعد الإقلاع

```
localStorage.sessionId + Terminal.id()
  ──▶ rpc app_session_whoami(session_id, terminal_id, max_age_hours)
        يفحص: مغلقة؟ · الجهاز مطابق؟ · تجاوزت العمر؟ · الموظف نشط؟ · مجهولة؟
        ثم يعيد الهوية والصلاحيات من قاعدة البيانات
```

جلسة أنشأها `anon` بلا `employee_id` تردّ `reason:"anonymous"` — وهذا ما يقطع
مسار انتحال V6.

## 4. نموذج الجلسة

| ما يُحفظ في `soufyan.erp.session.v1` | لماذا |
|---|---|
| `sessionId` | ادّعاء يُفحص عند كل إقلاع |
| `terminal` | ليقارنه الخادم، لا ليفحصه المتصفح |
| `employee` / `permissions` | **للعرض أثناء الانقطاع فقط** — تُستبدل بما يقوله الخادم عند أول ردّ |
| `at` | لحساب مهلة السماح محليًا |

**لا يُكتب إطلاقًا:** كلمة مرور · رمز PIN أو بصمته · رمز OTP · `access_token` ·
`refresh_token` · أي سرّ. (مُتحقَّق منه آليًا في `tests/security.mjs` بعد دخول كامل،
على `localStorage` و`sessionStorage` معًا.)

### الراية `verified`

أثناء انقطاع الشبكة تُعرض آخر هوية معروفة بشارة «بلا اتصال»، لكن `verified=false`
و`can()` تردّ `false`. السبب مباشر: من يحرّر التخزين ثم يقطع الشبكة عمدًا يقع في
هذا الفرع بالضبط. الشاشة تبقى، والسلطة لا تُمنح حتى تعود نبضة تؤكّدها.

### الأعمار والنبض

`sessionMaxHours` (١٢ افتراضًا) يُفرض **على الخادم** داخل `app_session_whoami`،
لا في المتصفح. النبضة كل `heartbeatSeconds` تعيد الهوية أيضًا، فتُصحّح ما عُرض
أثناء الانقطاع بدل أن تكتفي بإخفاء الشارة.

## 5. نموذج الجهاز (Terminal)

`Terminal.id()` **معرّف لا اعتماد**. لا يثبت شيئًا وحده، ولا يمنح صلاحية، ومحوه
لا يتجاوز أي حماية — أقصى أثره أن يُرفض استئناف الجلسة فيُطلب دخول جديد.

يستعمله الخادم لثلاثة أمور: ربط الجلسة بالجهاز، وتسجيل جلسات التشغيل، وحدّ
المحاولات. وبما أنه يرسله العميل، **لا يُبنى عليه حدّ محاولات وحده** — انظر §7.

## 6. نموذج كلمة المرور و PIN

### كلمة المرور

تُرسل إلى Supabase Auth ولا تُقارَن ولا تُخزَّن ولا تُسجَّل في المتصفح، ويُفرَّغ
الحقل فور النجاح أو الفشل. تقييم القوة في الواجهة **للإرشاد**؛ والفرض على الخادم.

> **مطلوب في لوحة التحكم:** فعّل *Leaked password protection*
> (Authentication ← Providers ← Email). المستشار يبلّغ عنها معطّلة اليوم.

### PIN

`verify_employee_pin(p_pin_hash, p_terminal_id)`:

* العميل يحسب بصمة، والخادم يتحقّق منها بـ **bcrypt** مقابل `employees.pin_hash`.
* bcrypt يجعل كل محاولة مكلفة على الخادم — وهذا يعمل لصالحنا.
* **لكن البصمة هي كلمة السرّ الفعلية**: من يقرؤها يدخل. هذا قيد معماري قائم،
  تغييره يتطلّب تعديل التطبيق الحيّ (§9).
* الرمز نفسه لا يُخزَّن ولا يُسجَّل في أي مكان، ولا يُشتقّ منه أي صلاحية في الواجهة.

## 7. تحديد المحاولات

| العملية | الحدّ | مَن يفرضه |
|---|---|---|
| الدخول بكلمة المرور | يردّ `429` | Supabase Auth |
| إرسال/تحقّق OTP | يردّ `429` | Supabase Auth |
| تحقّق PIN | ٥ لكل جهاز/دقيقتين · ١٠ لكل IP/١٠د · ٣٠ لكل IP/ساعة · ٨ معرّفات جهاز لكل IP/ساعة | `pin_attempts_blocked()` |
| `setup-provision` | ٦٠ لكل مستخدم/٥ دقائق | `rate_limit_hit()` |

**الفرع الأخير في حدّ الـPIN هو الإصلاح الجوهري.** الحدّ القديم كان يعتمد على
`p_terminal_id` وهو **وسيط يرسله العميل**، فتدويره في كل طلب يصفّر العدّاد. الآن
عدد معرّفات الأجهزة المختلفة من IP واحد هو نفسه شرط حظر — فصار الالتفاف هو ما
يُشغّل الحظر.

**ملاحظة على مصدر الـIP:** `request_client_info()` يقرأ `cf-connecting-ip` أولًا
(تضبطه Cloudflare ولا يستطيع العميل انتحاله)، ثم `x-real-ip` ثم أول قيمة في
`x-forwarded-for` — وهذان يرسلهما العميل. ما دام الطلب يمرّ عبر بوّابة Supabase
فالأول هو الفائز. أي نشر مستقبلي لا يمرّ بها يجعل حدّ الـIP قابلًا للتجاوز.

لا يوجد أي حدّ محاولات في الواجهة يُعتمد عليه أمنيًا.

## 8. RLS والصلاحيات

### الحقيقة المقاسة على هذا المشروع

`anon` و`authenticated` **لا يملكان أي GRANT على جداول `public`** عدا `SELECT`
على `activity_log` و`activity_feed`. و PostgREST يتصل بأحد هذين الدورين.

النتيجة العملية: سياسات مثل `products_rw … TO authenticated USING (true)`
**لا يمكن الوصول إليها** — يُرفض الطلب على مستوى الصلاحيات قبل تقييم RLS:

```
42501 permission denied for table profiles
```

فسطح الوصول الحقيقي كلّه **دوال `SECURITY DEFINER`**، وهذا يفسّر لماذا هي ٥٥
دالة ممنوحة لـ`anon`/`authenticated`. من يراجع أمان هذا المشروع يجب أن يراجع
الدوال، لا السياسات.

### جداول V7 الجديدة

`setup_state` · `setup_provision_runs` · `security_events` · `rate_limits` —
كلها RLS مفعّلة **بلا سياسة كتابة**، فالوصول عبر دوال `SECURITY DEFINER` وحدها.
الاستثناء الوحيد قراءة `security_events` للإداريين.

### قفل تصعيد الصلاحية

`profiles_self_write` تسمح بالتعديل بشرط `auth.uid() = id` **ولا تفرّق بين
الأعمدة**، و`role` عمود في الصف نفسه. غير مستغلّة اليوم (لا `UPDATE` لـ
`authenticated`)، لكن أول منح صلاحية يفتحها. المحفّز
`profiles_guard_privileged_columns` يغلقها على مستوى الجدول فيغطّي كل مسارات
الكتابة. مُتحقَّق منه:

```
42501 not authorised to change role or status
```

### دوال SECURITY DEFINER المضافة في V7

| الدالة | لمن | لماذا DEFINER | الحارس |
|---|---|---|---|
| `app_session_whoami` | anon, authenticated | تقرأ `app_sessions`/`employees` وهي محجوبة عن الأدوار العامة | الجهاز + العمر + الحالة + رفض الجلسة المجهولة |
| `app_session_start_authenticated` | authenticated | تكتب جلسة وتربط صف موظف | `auth.uid()` إجباري؛ لا يُقبل معرّف من العميل |
| `setup_status` | anon, authenticated | تقرأ `setup_state` المحجوب | تعيد أعلامًا فقط، بلا بيانات |
| `log_security_event` | لا أحد (مسحوبة) | تكتب سجلًّا | تُستدعى داخليًا فقط |
| `rate_limit_hit` | لا أحد (مسحوبة) | تكتب عدّادات | تُستدعى داخليًا فقط |

كلها `SET search_path` صراحةً.

## 9. ما لم يُطبَّق — بقرار صاحب المشروع

`supabase/migrations/20260831093000_v7_anon_surface_hardening.NOT_APPLIED.sql`

٢٥ دالة `SECURITY DEFINER` متاحة لـ`anon`، أي قابلة للاستدعاء من الإنترنت
بالمفتاح العلني وحده:

* **`purchase_login` + ١٨ دالة `purchase_*`** — واجهة مشتريات وموردين كاملة
  يحرسها رمز PIN من ٤–٦ أرقام.
* **`verify_employee_pin`** — مِعراف PIN عالميّ بلا اسم مستخدم.
* **`sync_push`** — كتابة صفوف اعتمادًا على معرّف جلسة، و`app_session_start`
  متاحة لـ`anon`.

لم تُطبَّق لأن التطبيق الحيّ لا يوجد مصدره هنا، وسحب `EXECUTE` قد يوقف نقطة البيع
أو قسم الشراء في منتصف يوم عمل. الملف يحمل خطة إطلاق متدرّجة، واستعلامات «قبل
التطبيق» لمعرفة ما يُستدعى فعلًا، وقسم تراجع كامل.

**هذا أعلى بند مفتوح في المشروع.**

## 10. سياسة الأسرار

| المفتاح | أين يجوز | أين لا يجوز |
|---|---|---|
| `anon` / publishable | الواجهة (علني بطبيعته) | — |
| `service_role` | دوال الحافة فقط (`Deno.env`) | الواجهة · المستودع · أي سجلّ |
| أسرار مزوّد البريد | خطّاف `auth-email` | الواجهة |

لا يوجد أي مفتاح خدمة في الواجهة، ولا في هذا المستودع. `setup-provision` يقرأ
`SUPABASE_SERVICE_ROLE_KEY` من بيئة الدالة التي تحقنها Supabase، ولا يعيده ولا
يسجّله.

**مطلوب قبل التشغيل:**

```bash
supabase secrets set SETUP_ALLOWED_ORIGINS="https://<نطاق-التشغيل>"
```

بدونه تسمح `setup-invoice` و`setup-provision` بعناوين التطوير المحلية وحدها.

## 11. سياسة السجلّات

**لا يُسجَّل إطلاقًا:** كلمات المرور · رموز PIN وبصماتها · رموز OTP · رموز الوصول
والتحديث · أسرار مفاتيح المرور.

`log_security_event()` يحمل حارسًا يُسقِط أي مفتاح يشبه السرّ من `detail` مهما
أرسل النداء:

```sql
coalesce(p_detail,'{}') - 'password' - 'pin' - 'pin_hash' - 'otp'
                        - 'code' - 'token' - 'access_token' - 'refresh_token' - 'secret'
```

**ما يُسجَّل في `security_events`:** نوع الحدث · النتيجة · الوقت · `auth.uid()` ·
معرّف الموظف · معرّف الجهاز · IP · وكيل المستخدم · تفاصيل غير حسّاسة.

الأحداث المغطّاة: `login.success` · `login.disabled` · `session.terminal_mismatch` ·
`profile.role_change` (نجاحًا وحظرًا) · `setup.<task>`.

## 12. معالجة الأخطاء

كل فشل يصل المستخدم كسبب مغلق: **لا SQL، ولا مسار ملف، ولا نصّ استثناء، ولا رمز
داخلي، ولا رمز جلسة.** التفصيل يبقى في سجلّ الدالة على الخادم.

`Sb._err()` يحوّل ردود الخادم إلى `code` واحد تعرفه الواجهة، وتترجمه إلى رسالة
تجيب ثلاثة أسئلة: ماذا حدث، ولماذا، وماذا أفعل الآن. مُتحقَّق منه: خطأ خادم يحمل
`relation "auth.users" does not exist` و`SELECT … WHERE email = $1` ومسار
`token.go:214` لا يظهر منه شيء على الشاشة.

**عدم كشف الحسابات:** «نسيت كلمة المرور» تردّ الردّ نفسه سواء كان البريد مسجَّلًا
أو لا.

## 13. CSP والترويسات

CSP في `<meta>` داخل `index.html` لتعمل حتى عند فتح الملف مباشرةً. أهمّ ما فيها:

```
connect-src 'self' https://tyfidwamnlraysqrfdgb.supabase.co
object-src 'none'; base-uri 'self'; form-action 'self'
```

`connect-src` مثبَّتة على مشروع واحد: حتى لو نجح حقن نصّ، لا يستطيع إرسال شيء
إلى خادم آخر. **غيّرها إن غيّرت `supabaseUrl`.**

`frame-ancestors` و HSTS و `X-Frame-Options` لا تعمل داخل `<meta>` — الترويسات
الكاملة في [`deploy/security-headers.conf`](deploy/security-headers.conf).

### `script-src 'unsafe-inline'` — تنازل مقصود

التطبيق ملف واحد بلا خطوة بناء، وفتحه بنقرة مزدوجة خاصيّة أساسية فيه. البديل
جاهز:

```bash
node tools/build-csp.mjs           # يستبدل unsafe-inline ببصمات SHA-256
node tools/build-csp.mjs --check   # بوّابة CI
node tools/build-csp.mjs --revert
```

ليس مفعّلًا افتراضيًا لأن أي تعديل على الصفحة بعده يوقفها بالكامل حتى يُعاد
تشغيل الأداة. **لا توجد أي معالِجات أحداث سطرية في الصفحة** (مُتحقَّق منه آليًا)،
فالترقية نظيفة متى أُريدت.

  بدل ١ بعد تحرير `localStorage`. اختبار ينجح على النسخة المكسورة لا قيمة له،
  وهذه ليست كذلك.
* **PoC على قاعدة الإنتاج** عبر SQL: انتحال الجلسة، ربط الجهاز، تصعيد الصلاحية،
  دورة دخول واستئناف كاملة — ثم نُظّف الأثر ورُوجع أن الإنتاج لم يُمسّ.
* **مستشارو أمان Supabase**: ٧٩ ملاحظة، مصنَّفة في `AUDIT-V7.md`.

### Strix — لم يُشغَّل

مثبَّتة مهاراته في `.agents/skills/` (تسع مهارات)، لكنه **لم يُنفَّذ**، لأربعة
أسباب مستقلّة كلٌّ منها كافٍ وحده:

| المتطلَّب | الحالة هنا |
|---|---|
| Python ≥ 3.12 | **3.11.15** — `pip install strix-agent` يردّ `No matching distribution` |
| Docker daemon | العميل مثبَّت والخدمة غير متاحة (`docker info` يفشل) |
| `strix.ai` / `app.strix.ai` | **محجوبان** بسياسة بوّابة الخروج (`connect_rejected`) — لا CLI ولا Cloud API |
| مفتاح LLM | `LLM_API_KEY` و`STRIX_LLM` غير مضبوطين |

لتشغيله على بيئة تسمح بذلك:

```bash
export STRIX_LLM="anthropic/claude-opus-4-5"
export LLM_API_KEY="<مفتاحك>"
strix -n -t ./soufyan-erp-setup --scan-mode standard --max-budget 10
strix -n -t https://<نطاق-الإعداد>  --max-budget 20
```

اختبر ما تملك صلاحية اختباره فقط. وابدأ من §9 — فهو أعلى بند مفتوح، وسيجده أي
فحص جادّ.
