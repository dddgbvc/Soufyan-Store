# البنية المعمارية — Architecture

## الطبقات

```
المتصفح / الهاتف
        │
        ▼
  proxy.ts                  كوكيز CSRF والجهاز + ترويسات الحماية
        │
        ▼
  Route Handlers            التحقق من CSRF ثم تمرير الطلب
  (src/app/api/**)
        │
        ▼
  Authentication Layer      من أنت؟   (src/server/auth/**)
        │
        ▼
  Authorization Layer       ما الذي يُسمح لك به؟   (src/server/authz/**)
        │
        ▼
  Repositories              استعلامات SQL صريحة   (src/server/db/**)
        │
        ▼
  PostgreSQL (schema: erp_auth)
```

كل سهم في المخطط أعلاه هو حدّ ثقة: ما يصعد من الأسفل بيانات، وما ينزل من الأعلى
مُتحقَّق منه. لا يوجد مسار يتخطّى طبقة.

---

## لماذا اتصال مباشر بـPostgres بدل Data API؟

مخطّط `erp_auth` يحتوي على hash رموز الدخول والجلسات وتحديات QR. لو عُرض عبر
PostgREST لأصبح مفتاح `anon` المسرَّب نقطة هجوم على مادة الاعتماد نفسها.

بدل ذلك:

- الجداول **غير معروضة** على Data API إطلاقاً.
- الأدوار `anon` و`authenticated` مسحوبة الصلاحيات على المخطط كاملاً.
- RLS مفعّلة فوق ذلك كطبقة ثانية مستقلة.
- الخادم يتصل مباشرة عبر `DATABASE_URL`، وهو الطرف الوحيد الذي يملك السرّ.

النتيجة: تسريب مفتاح المتصفح لا يقترب من جدول واحد في هذا المخطط.

Supabase Auth ما زال مستخدماً — لكن لدوره الصحيح فقط: التحقق من كلمة المرور.
النظام لا يخزّن كلمات مرور ولا يراها.

## فصل المسؤوليات

| الوحدة | المسؤولية | لا تفعل |
|---|---|---|
| `server/security/crypto` | scrypt، HMAC، الرموز العشوائية | لا تلمس قاعدة البيانات |
| `server/security/validation` | التحقق من الشكل وسياسة قوة الرمز | لا تقرّر الصلاحيات |
| `server/security/csrf` | مصدر الطلب والرمز المزدوج | — |
| `server/auth/session` | إصدار الجلسات والتحقق منها | لا تعرف الكوكيز إلا في القسم المخصص لها |
| `server/auth/pin` | تعريف الموظف من الرمز | لا تكتب كوكيز |
| `server/auth/otp` | استرجاع الرمز عبر البريد | لا تكشف وجود الحساب |
| `server/auth/qr` | تحديات الدخول عبر الهاتف | لا تصدر جلسة قبل الاستهلاك |
| `server/authz/guard` | هل يملك هذا الموظف هذه الصلاحية؟ | لا تصادق |
| `server/db/repositories` | SQL فقط | لا تتخذ قرارات أمنية |

الفائدة العملية: طبقة المصادقة **لا تعرف HTTP**. تأخذ `RequestContext` وتُعيد نتيجة،
ولذلك تُختبر مباشرة بدون خادم — وهذا ما تفعله مجموعة الاختبارات.

## تدفّق طلب كامل (دخول بالـPIN)

```
POST /api/auth/pin  { pin: "••••••" }
  │
  ├─ proxy.ts             يضمن وجود كوكي CSRF وكوكي الجهاز
  │
  ├─ assertCsrf()         Origin مطابق + الرمز المزدوج متطابق
  │
  ├─ parseBody(schema)    ٦ أرقام بالضبط، وإلا 400
  │
  ├─ getRequestContext()  IP + الجهاز + بصمة العميل
  │
  ├─ loginWithPin()
  │    ├─ consume_rate_limit()      عدّاد ذرّي في قاعدة البيانات
  │    ├─ blindIndex(pin)           فهرس أعمى بمفتاح الخادم
  │    ├─ findCredentialsByPinLookup()
  │    ├─ verifySecret(scrypt)      التحقق القاطع
  │    ├─ فحص الحالة والإيقاف المؤقت
  │    ├─ issueSession()            رمز عشوائي، يُخزَّن كـSHA-256
  │    └─ audit.record()
  │
  ├─ setSessionCookie()   httpOnly + SameSite=Lax + Secure في الإنتاج
  │
  └─ { employee, permissions, modules }
```

## لماذا الجلسات على الخادم؟

الرمز في الكوكي عشوائي بحت ولا يحمل أي معنى. كل ما يخصّ الجلسة — الموظف، الصلاحية
الزمنية، الجهاز، حالة الإبطال — يعيش في قاعدة البيانات.

يترتب على ذلك مباشرة:

- **الإبطال فوري.** تعطيل موظف أو تغيير رمزه ينهي جلساته في نفس اللحظة.
- **لا صلاحيات في الكوكي.** لا يمكن لأحد أن يزوّر صلاحية لأنها ليست في يده أصلاً.
- **تسريب قاعدة البيانات لا يُنتج جلسة.** المخزَّن hash، والرمز الأصلي لا يُخزَّن.

الصلاحيات تُقرأ من قاعدة البيانات في كل طلب محمي، لا من نسخة محفوظة في المتصفح.
