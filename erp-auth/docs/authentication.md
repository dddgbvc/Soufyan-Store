# تدفّقات المصادقة — Authentication Flows

## ١. الدخول بالـPIN

الواجهة لا تعرض أي اسم موظف. المطلوب ستة أرقام فقط.

```
الموظف يُدخل ٦ أرقام
        │
        ▼
POST /api/auth/pin
        │
        ├─ تحديد المعدّل حسب (IP + كوكي الجهاز)
        ├─ blindIndex(pin) = HMAC(lookupKey, "pin:" + pin)
        ├─ SELECT … WHERE pin_lookup = $1        ← بحث واحد مفهرس
        ├─ verifySecret(pin, pin_hash)           ← التحقق القاطع
        ├─ فحص status و locked_until
        ├─ تصفير عدّاد المحاولات لهذا العميل
        ├─ إصدار جلسة + تسجيل الدخول
        └─ تسجيل في سجل التدقيق
        │
        ▼
"هلا بيك {الاسم} 👋"  →  لوحة التحكم
```

### كيف يُعرف الموظف من الرمز وحده؟

المشكلة: بدون اسم أو رقم موظف، كيف نجد صاحب الرمز؟ مقارنة الرمز بـ hash كل موظف
تعني تشغيل scrypt مرة لكل موظف في كل محاولة — تكلفة تتضاعف مع كل توظيف.

الحل: **فهرس أعمى (blind index)** — عمود `pin_lookup` يخزّن
`HMAC-SHA256(lookupKey, "pin:" + pin)`، حيث `lookupKey` مشتق من `AUTH_PIN_PEPPER`
الذي لا يُخزَّن في قاعدة البيانات إطلاقاً.

- الخادم يحسب نفس القيمة ويجدها بفهرس فريد: O(1) مهما بلغ عدد الموظفين.
- من يسرق قاعدة البيانات وحدها لا يستطيع تجربة المليون احتمال، لأن الدالة مفتاحية
  والمفتاح ليس عنده.
- `pin_hash` (scrypt) يبقى هو الحكم النهائي: تطابق الفهرس يوجّه فقط، ولا يُقبل
  كإثبات. اختبار `digest_mismatch` يغطي هذا المسار.

**المقايضة، بصراحة:** من يسرق قاعدة البيانات **و** المتغيّر السرّي معاً يستطيع
استخراج الرموز. فضاء ٦ أرقام صغير بطبيعته. لذلك الدفاع الحقيقي هو تحديد المعدّل
والتعطيل التدريجي، لا صعوبة الـhash. راجع [security.md](security.md).

### التفرّد إلزامي

فهرس فريد على `pin_lookup` يمنع أن يحمل موظفان الرمز نفسه — وإلا صار «من صاحب هذا
الرمز؟» سؤالاً بلا إجابة واحدة. محاولة تعيين رمز مستخدم تُرجع `pin_taken`.

### الحماية من التخمين

| الطبقة | التفصيل |
|---|---|
| نافذة المحاولات | ٥ محاولات لكل (IP + جهاز) خلال ٥ دقائق |
| الحظر المتصاعد | ١٢٠ ثانية ثم ٢×، ٤×، ٨×، ١٦× بحدّ أقصى ساعة |
| الرمز الصحيح لا يفكّ الحظر | العميل المحظور يبقى محظوراً |
| نطاق الحظر | على العميل المخالف فقط — صندوق آخر في المحل يعمل طبيعياً |
| زمن ثابت | عند عدم وجود تطابق يُشغَّل scrypt وهمي، فلا يكشف الزمن وجود الرمز |
| رسالة موحّدة | «بيانات الدخول غير صحيحة» لكل أسباب الفشل |

الحسابات المعطّلة تُرفض حتى مع رمز صحيح، ولا يُصدَر لها أي جلسة.

## ٢. الدخول بالبريد وكلمة المرور

طريقة ثانوية داخل «طرق دخول أخرى». النظام **لا يخزّن ولا يرى** كلمات المرور:
Supabase Auth يتحقق، ثم يُترجَم المستخدم إلى موظف ERP وتُصدر جلسة النظام نفسها.

```
POST /api/auth/password
  ├─ تحديد المعدّل حسب العميل وحسب البريد
  ├─ supabase.auth.signInWithPassword()
  ├─ employees WHERE auth_user_id = user.id
  │     └─ أو الربط بالبريد عند أول دخول
  ├─ فحص status و locked_until
  └─ إصدار جلسة ERP
```

حساب صالح في Supabase بلا سجل موظف **ليس** دخولاً: يُرفض ويُسجَّل كحدث حرج.

عند تعطيل Supabase في البيئة تختفي الطريقة من الواجهة وتُرجع نقطة النهاية
`unavailable`، بينما يبقى الدخول بالرمز وQR يعملان.

## ٣. نسيت رمز الدخول (OTP)

```
البريد
  ▼
POST /api/auth/otp/request
  ├─ حدّان: لكل عميل ولكل بريد
  ├─ توليد ٦ أرقام بـrandomInt (لا Math.random)
  ├─ تخزين scrypt للرمز في نطاق otp
  ├─ إلغاء أي رمز سابق لنفس الموظف
  └─ إرسال البريد
  ▼  الجواب موحّد سواء وُجد البريد أو لا
الرمز
  ▼
POST /api/auth/otp/verify
  ├─ claimAttempt()  ← زيادة ذرّية للعدّاد
  ├─ verifySecret()
  └─ إصدار resetToken لمرة واحدة (١٠ دقائق)
  ▼
الرمز الجديد + التأكيد
  ▼
POST /api/auth/otp/reset
  ├─ فحص قوة الرمز أولاً
  ├─ [معاملة] استهلاك المقبض + كتابة الرمز + إلغاء بقية الرموز + تدقيق
  └─ إنهاء كل جلسات الموظف
```

**ما لا يفعله هذا التدفّق**

- لا يكشف إن كان البريد مسجّلاً — نفس الجواب ونفس الشكل في الحالتين.
- لا يرسل الرمز القديم ولا يلمّح إليه.
- لا يخزّن OTP كنص صريح.
- لا يقبل الرمز مرتين، ولا بعد نفاد المحاولات (٥)، ولا بعد ١٠ دقائق.

**لماذا معاملة في الخطوة الأخيرة؟** استهلاك المقبض وكتابة الرمز يجب أن ينجحا أو
يفشلا معاً. بدون ذلك، رمز جديد ضعيف أو مستخدَم يحرق المقبض ويجبر الموظف على إعادة
الرحلة كاملة. الاختباران `keeps the reset handle usable after a rejected weak PIN`
و`… when the chosen PIN is already taken` يحرسان هذا السلوك.

نجاح إعادة التعيين يُنهي **كل** الجلسات: الاسترجاع غالباً يعني أن الرمز القديم كان
في اليد الخطأ.

## ٤. QR PASSKEY

جهازان: الشاشة المنتظِرة، وهاتف الموظف.

```
الشاشة                                   الهاتف
──────                                   ──────
POST /api/auth/qr/challenge
  → token (داخل الصورة)
  → pollSecret (في ذاكرة التبويب)
  → device cookie (موجود أصلاً)
  → عرض QR
        │
        │  يمسح الرمز ──────────────────▶  /approve#t=<token>
        │                                  POST /api/auth/qr/inspect
        │                                    → pending / expired
        │                                  الموظف يدخل رمزه أو بريده
        │                                  POST /api/auth/qr/approve
        │◀──────────────────────────────────  ✓
POST /api/auth/qr/status  (استطلاع)
  → approved
POST /api/auth/qr/consume
  → جلسة على الشاشة  →  لوحة التحكم
```

### ما بداخل رمز الـQR

`{APP_URL}/approve#t=<token عشوائي ٣٢ بايت>`

لا بريد، لا معرّف موظف، لا رمز دخول، لا أي مادة اعتماد. مجرد مقبض عشوائي قصير
العمر.

الرمز يسافر في **جزء العنوان (fragment)** — والمتصفحات لا ترسل هذا الجزء إلى
الخادم إطلاقاً. لذلك لا يظهر في سجلات الوصول ولا في ترويسة `Referer`. الصفحة
تقرأه من `location.hash`، تمسحه فوراً من شريط العنوان، وترسله في جسم POST.

### ثلاثة أسرار منفصلة

| السرّ | من يملكه | يمنع |
|---|---|---|
| `token` | الهاتف الماسح | الموافقة بدون رؤية الشاشة فعلاً |
| `pollSecret` | التبويب المنشئ | استطلاع تحدٍّ لا يخصّك |
| كوكي الجهاز | متصفح الشاشة | استهلاك التحدي من جهاز آخر |

الاستهلاك يتطلّب **الأخيرين معاً**. اختبار
`refuses consumption from a different device, even with the poll secret` يثبت أن
سرقة سرّ الاستطلاع وحده لا تكفي.

### الاستخدام لمرة واحدة

الاستهلاك جملة `UPDATE` شرطية واحدة:

```sql
UPDATE qr_login_challenges
SET status = 'consumed', consumed_at = now()
WHERE id = $1 AND status = 'approved' AND expires_at > now()
  AND poll_secret_hash = $2 AND device_binding_hash = $3
RETURNING …
```

الانتقال من `approved` إلى `consumed` **هو** آلية الاستبعاد المتبادل: أول طلب
يحصل على صف، والثاني على لا شيء. اختبار
`lets only one of two racing redemptions win` يطلق طلبين متوازيين ويؤكد أن واحداً
فقط ينجح.

الموافقة كذلك ذرّية: `pending → approved` بشرط عدم الانتهاء، فالموافقة مرتين
مستحيلة.

### العمر والإلغاء

- العمر الافتراضي دقيقتان (`QR_TTL_SECONDS`).
- الموافقة تمدّد المهلة ٦٠ ثانية فقط ليلحق الاستهلاك.
- إغلاق شاشة الدخول يستدعي `/qr/revoke` — لا يبقى رمز معلّق.
- المسح بعد الانتهاء يُرجع `qr_expired`، وبعد الاستهلاك `qr_invalid`.

### الموافقة مصادقة كاملة

المسح لا يمنح شيئاً. الهاتف يجب أن يقدّم رمز دخول صحيحاً أو بريداً وكلمة مرور
صحيحين، ويمرّ ذلك بنفس فحوص المعدّل والحالة والإيقاف. موافقة بمادة خاطئة تترك
التحدي `pending` كما كان.

## ٥. الجلسات

| الجانب | القيمة |
|---|---|
| الرمز | ٣٢ بايت عشوائية، base64url |
| التخزين | SHA-256 فقط — الرمز الأصلي لا يُكتب |
| الكوكي | `httpOnly` + `SameSite=Lax` + `Secure` في الإنتاج |
| الخمول | ٦٠ دقيقة، تتجدّد مع كل طلب |
| السقف المطلق | ١٢ ساعة، لا يتمدّد مهما كان النشاط |
| التجديد | داخل نفس الاستعلام الذي يتحقق من الجلسة |
| التدوير | بعد تغيير الرمز يُصدَر رمز جديد ويُبطَل القديم |

**ما يُنهي الجلسة فوراً:** الخروج، تجاوز أي من المهلتين، تعطيل الموظف، إيقافه
مؤقتاً، تغيير رمزه، إعادة تعيين رمزه، إنهاء المدير لجلساته، أو إنهاء الموظف لها
من شاشة «أجهزتي».

`localStorage` لا يُستخدم للمصادقة إطلاقاً.
